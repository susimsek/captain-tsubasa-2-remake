# Fresh KICK OFF Selector Timing and `$893B` IRQ Candidate

## Scope and provenance

This report covers the ROM transition from `$80FA->$A20F` match selection into
the `$893B` preset wait for the canonical recorded KICK OFF input route. The
supplied ROM SHA-256 is
`4f1f74d495e86025a5ad17fec2c171f37a94541a7d8ff7034c580d7d5111a097`; the
input-route SHA-256 is
`6cae92ff2b6a77fcc05c34c57c734bbff47930ada172633cb4a4b830cc3e77dc`.

FCEUX evidence comes from the two-pass muted NTSC/NewPPU replay in
`reference/diagnostics/kickoff_select_cleanup_counters_20261031_004228_utc/`.
The trace was resumed from its verified frame-4692 checkpoint. FCEUX observations
validate the route; they are not runtime inputs. The ROM-only candidate schedule
is generated by
`tools/gameplay/build_fresh_kickoff_irq_source_schedule.py` from ROM bytes and
the recorded input sequence. It uses the diagnostic Py65 runner at build time,
does not load FCEUX state, and is retained under `reference/`, not the runtime
asset tree.

## Selector call timing

The muted FCEUX caller hooks show bank `$02` entering `$A20F` at source frame
7258, CPU cycle 216,143,878, and returning through `$A8B6` at source frame 7266,
cycle 216,367,117. The call spans 223,239 CPU cycles and crosses eight source
frame labels. The repeated pass agrees. The hooks file is
`reference/diagnostics/kickoff_select_cleanup_counters_20261031_004228_utc/caller_hooks.csv`.

The hash-checked Godot selector executor in
`scripts/gameplay/rom_fresh_match_selector_executor.gd` decodes the ROM copy of
4,944 bytes from `$ACB0-$BFFF` to PRG RAM `$6000-$734F`, then copies eleven
match-zero player IDs. Its bounded mainline takes 203,333 cycles. The candidate
clock model accounts for another 19,909 cycles as eight NMIs and seven IRQs,
for 223,242 elapsed cycles. FCEUX measures 223,239 cycles; the candidate entry
is three cycles earlier under the tools' hook conventions, while the return
cycle matches.

The executor now exposes `ram_write_timeline` and
`apply_ram_write_timeline_through_cycle()`. The timeline timestamps the ROM
copy, its pointer updates, the nested JSR stack push when a physical stack is
present, roster writes, and match-state stores. The focused selector verifier
passes cycle ordering, prefix materialization, final RAM reconstruction, and
both physical/logical stack paths.

The live route now consumes the timeline using
`scripts/gameplay/rom_fresh_match_selector_clock.gd` and the validated
`assets/gameplay/rom_logic/fresh_match_selector_runtime_clock.json`. It applies
write prefixes over relative frame offsets 0–8 and reaches `$893B` at frame
7266. The integration verifier checks the per-frame cycle cursor, all final
selector RAM, and 15 scheduled interrupt events.

This is not a resumable CPU. The ROM executor computes the full return result
at call entry; the route delays exposing RAM writes until each cycle budget.
The runtime clock records interrupt accept/return positions but does not apply
handler writes or return receipts. Intermediate visible output has not been
compared for every frame, so this timing work does not establish visible
frame parity.

## `$893B` wait and candidate edge

The ROM-only candidate run locates the target wait by requiring ROM-derived RAM
`$001B=$C0`, `$0078=$04`, `$0079=$40`, `$003B=$55`, and the physical caller
return word `$8116`. This avoids unrelated executions of the same `$893B` PC.
It produces an MMC3 IRQ edge at source frame 7266, CPU cycle 216,372,246, PPU
line 128/dot 274. The candidate then executes the hash-checked ROM IRQ wrapper
and `$A160` service, writes `$0078:$04->$00` at `$A1C3` cycle 216,372,408, and
returns through `$C4AD` to `$893B` with the interrupted stack and registers
restored.

The candidate wait state has `P=$30`, whose I bit (`$04`) is clear. The FCEUX
`$8114` hook reports `P=$22`, also with I clear; runtime does not use that
emulator value. Cold-reset source bytes execute `$C6B8 CLI` before the title
route, as recorded in
[`fresh_kickoff_1b6_boot_producer_20261029.md`](fresh_kickoff_1b6_boot_producer_20261029.md).
The runtime clock asset now carries only `I=clear` from the hash-bound
ROM-only source CPU candidate. `KickoffRouteRuntime` adds that single known bit
to the selector input and preserves it through normalization and the `$893B`
prefix; the route verifier checks the mask and value. This is not a full P byte,
not a live Godot CPU execution from `$C6B8`, and not physical timing proof. The
candidate uses a simplified PPU/MMC3 schedule, while the actual IRQ/NMI handlers
and their RTI effects are still not executed by the route.

The FCEUX trace records the `$A1C3` store at cycle 216,372,411, three cycles
after the candidate under their respective hook conventions. This is useful
software-model agreement, not proof of physical NES timing. The candidate PPU
does not model the complete fetch pipeline and uses a simplified MMC3 scanline
hook. The selector event schedule is connected to route timing, but the
candidate wait handler is not connected to production.

The ROM-only candidate artifact is
[`fresh_kickoff_893b_irq_candidate_schedule_20261031.json`](fresh_kickoff_893b_irq_candidate_schedule_20261031.json).
The reviewed selector clock is converted into the project-owned runtime asset
`assets/gameplay/rom_logic/fresh_match_selector_runtime_clock.json`; its
consumer rejects changed ROM identity, malformed call boundaries,
noncontiguous frame spans, and incorrect totals. It marks handler effects and
return receipts unapplied. Runtime must execute the ROM handlers and derive
the `$0078` write and RTI receipt itself; no live consumer does so.

## Production title-to-wait context handoff audit — 31 Oct 2026

There is no complete machine-state handoff from the title/opening runtime into
the `$893B` wait. `OpeningSourceRuntime._on_kickoff_requested()` stops opening
audio, freezes and hides `ColdStartSourceCommandPresenter`, then instantiates
`KickoffRouteRuntime`; it passes no CPU or hardware context. `RomTitleMenu`
emits `kickoff_requested` without a payload. The presenter's public `state`
contains cutscene, scheduler, named pseudo-RAM, and presentation data, while
`freeze_source_for_title_handoff()` only stops its processing. It has no CPU
register file, physical stack, full RAM, mapper register image, or current
PPU/MMC3 phase. `TitleRomHandoffQueue` applies title background/palette/cursor
packets and records NMI/capacity events; it is not a machine-state emulator.
The route then starts an independent cutscene VM in `KickoffRouteRuntime._ready()`.

The earliest break in live CPU/hardware continuity is the KICK OFF UI signal
and route startup: it freezes the opening presenter and starts a new cutscene
VM without a source CPU/hardware context. Later, the `$80F1` cleanup/caller
contract also has only partial registers and an abstract SP; `$80F7->$C4B9`
receives the ROM-derived `$0022` but uses a logical JSR frame instead of a
physical caller stack. The normalizer/preset prefix can derive
`$EA/$25/$EC/$ED` and the partial P contract, but it cannot recover the
unmodeled machine history. In particular, no current production input
produces wait-control RAM `$001B/$0078/$0079/$003B`, absolute SP and stack-page
bytes, full P, PPU beam/register/fetch state, or MMC3 register/A12/IRQ state.
The opening presenter's `$0079` title-raster model is not evidence for the
fresh-match `$0079` wait value and must not be reused.

Therefore the route must remain fail-closed at `$893B`. Do not create a
`$893B` context by copying the candidate JSON's wait state or FCEUX RAM, and do
not consume the tail continuation without a ROM-executed interrupt receipt.
The next production increment must carry a live ROM-owned machine context
through the KICK OFF route to the wait, then compare its independently
produced wait and RTI state against same-input FCEUX. Existing partial
producers remain reusable for mapper shadow, preset pointer/bank, and the
single-bit I-clear contract only.
