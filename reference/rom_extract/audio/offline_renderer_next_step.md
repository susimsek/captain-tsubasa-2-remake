# Offline renderer: faithful next step

## Recommendation

Keep the current Godot WAV as the only shipped audio source for now. It is
already generated by executing the supplied ROM's sound driver and PRG data
through the offline NSF wrapper and libgme; it does not use captured gameplay
PCM and needs no ROM, NSF, or emulator at Godot runtime. Do not replace it with
the FCEUX gameplay recording or the unexplained 4,700-frame probe.

The shortest path to better fidelity is to keep the source-derived NSF and
event provenance, then replace or improve the **offline synthesis stage** with
a reproducible renderer that follows the selected APU output reference. Treat
FCEUX output as the comparison target while implementing that renderer; under
the project's current rule that emulator WAVs are validation-only, do not
ship PCM written by FCEUX. A FCEUX-rendered NSF is generated from ROM source
bytes rather than copied from a gameplay recording, but it is still PCM
recorded from an emulator. The wording does not explicitly settle whether that
kind of generated PCM can ship, so the safe interpretation is to keep it
diagnostic and generate the distributable asset with a project-owned,
ROM-source-driven synthesis step.

## ROM-source WaveHi head-to-head (25 Oct 2026)

A fresh diagnostic render was generated from the ROM-derived NSF APU write
stream, the ROM's bank-$1E DPCM bytes, and the pinned FCEUX WaveHi mixer/filter
model. It was compared at identical sample indices against both the current
Godot libgme WAV and same-input FCEUX PCM. In the 60,905-sample first music
window before DMC begins (frames 283–365), source WaveHi correlation to FCEUX
is 0.961970 with normalized RMSE 0.278799; the current runtime WAV is 0.162994
and 1.145917. This is a meaningful improvement for that isolated window.

It is not a safe runtime replacement: on the first DMC window (frames 367–449),
WaveHi correlation falls to -0.054778 and normalized RMSE rises to 1.479247;
the runtime is 0.147628 and 1.418269. Later windows also remain mixed. The
source candidate uses a global clock fit with up to 0.691 ms register-write
residual, and DMC DMA/frame-sequencer callbacks are modeled at CPU-cycle rather
than instruction-hook boundaries. The candidate stays diagnostic-only; runtime
WAV hash is unchanged. Full same-window metrics and hashes:
`reference/diagnostics/audio/rom_source_wavehi_improvement_20261025/README.md`
and its `head_to_head_comparison.json`.

## What the existing build already proves

`tools/audio/build_opening_timeline_nsf.py` checks the supplied ROM SHA-256
`4f1f74d495e86025a5ad17fec2c171f37a94541a7d8ff7034c580d7d5111a097`, copies
its PRG banks into an NSF intermediate, and changes five byte-checked MMC3
`STY $8001` writes into calls to an NSF-only bank trampoline. All other PRG
bytes are retained. The wrapper schedules the observed sound IDs at their
captured `$0700` frame positions, then calls the original driver once per NTSC
frame. The 12 `ED` command IDs/origins and the Start stop event have live
CPU/MMC3/ROM-byte evidence; the absolute cue frames still come from one saved
input replay, not from a complete source scheduler.

`tools/audio/render_opening_timeline.py` executes that intermediate through
libgme 0.6.5, preserves initial silence, removes the measured three-frame
libgme onset delay, and packages frames 0–4661 as
`assets/opening/audio/opening_timeline_rom_driver.wav`. The WAV SHA-256 in the
current audit is `325fa7947fcba0874a6b5261a03b8314d302df318a58f887eb0ee4daab8cbf4a`.
Its metadata explicitly says captured PCM was not used and the runtime needs
neither ROM nor emulator. This is a source-derived render, not a byte-for-byte
copy of a ROM WAV (the ROM stores driver/sequence data, not this PCM file).

Current limits are material: later cue envelopes do not line up consistently
(the broad comparison peaks at 0.523 correlation), sample-level timbre and
individual effects are unverified, and the Godot controller stops the mixed
WAV immediately on Start. The original's APU channels become silent on frame
4662, but its output filter continues a low-level tail through frame 4679.
The fixed captured path therefore needs the WAV to continue into the black
transition if that tail is to be represented. Arbitrary Start timing and
independently triggered cues need the ROM scheduler/driver state, not just the
fixed captured event table.

## Sample/frame alignment evidence

Use the precise same-input capture only as a validation index. Its 4,693 CSV
rows cover source frames 0–4692, but row 0 has zero elapsed CPU cycles. Rows
1–4692 total 139,730,109 CPU cycles. At 44.1 kHz and the pinned NTSC CPU clock,
that is 3,442,949.88576 raw samples. The FCEUX `soundq=2` FIR startup phase is
1,025 clock units (25.256 samples), predicting 3,442,924.62976 samples; rounding
matches the observed 3,442,925. These values and the capture hash are recorded
in `reference/diagnostics/audio/precise_pcm_sample_alignment_20261024.json`.
Align by emulated-cycle/sample boundaries and FIR priming, not by multiplying
the CSV row number by a nominal frame length.

The separate Lua/NSF probe requested 4,700 `frameadvance` calls and wrote
3,461,217 samples (nominally 4,716.89 NTSC video frames). Its per-frame cycle
and sample counts were not recorded, so its length remains unexplained. It
cannot establish a tail offset. The precise capture-boundary correction does
not solve the tail synthesis: applying only FCEUX's final `SexyFilter`
recurrence to libgme output still fails because the upstream mixer/resampler
state differs.

## Renderer architecture and next work

The pinned FCEUX source shows the high-quality path in `FlushEmulateSound()`:
APU channel synthesis writes the `WaveHi` buffer; `NeoFilterSound()` performs
the stateful FIR/resampling and retains `mrindex`/history through its leftover
buffer; `SexyFilter()` then carries `acc1` and `acc2` across calls; finally
`FCEU_WriteWaveData()` serializes the returned samples. The same source also
contains optional `SexyFilter2`, but the recorded capture profile had low-pass
disabled. This explains why copying just the final filter formula onto libgme
PCM is insufficient.

### CPU-cycle ROM-driver trace now available

`tools/audio/trace_rom_driver_apu.py` builds a temporary, instrumented copy of
libgme 0.6.5 after verifying pinned upstream source hashes. Its temporary
entry advances `Nsf_Emu::run_clocks()` directly to the precise
139,730,109-cycle horizon from the same-input FCEUX capture. All GME output
voices are muted; no PCM is generated or written. The ROM-derived NSF executes
twice with byte-identical traces: 45,455 writes to `$4000–$4017` and 4,692
driver PLAY calls. The trace includes 903 DMC-register writes, so a future
renderer must implement DMC playback/fetch timing in addition to pulse,
triangle, and noise.

The traces and provenance are in
`reference/diagnostics/audio/rom_driver_apu_trace_20261024/`. The NSF wrapper
still queues ROM-proven cue IDs at the FCEUX replay's frame positions; the cue
schedule is not yet produced by a complete source scheduler. Instrumentation
captures register writes and same-cycle order, not CPU PC, WaveHi, or DMC fetch
events. The verified `$C000–$DFFF` NSF mapping exposes source PRG bank `$1E`,
where the original DPCM bytes are stored; the extract is retained under
`reference/rom_extract/audio/`.

Status of the proposed slices:

1. **Diagnostic source synthesis is implemented.** The ROM-derived APU writes,
   reset state, mapped DPCM bytes, pulse/triangle/noise/DMC contributions, and
   pinned WaveHi nonlinear mix feed a project-owned renderer. It consumes the
   measured FCEUX DMC and frame-update event timeline rather than executing
   the full 6502/DMA opportunity loop.
2. **The filter stage is implemented.** The pinned `soundq=2` FIR/resampler,
   1,025-sample overlap, and stateful `SexyFilter` are applied with the
   measured frame-cycle boundary data.
3. **Same-input validation is recorded.** The FCEUX PCM capture is consumed
   only by the comparison script. The latest ChannelBC-aware metrics and hashes
   are in `reference/diagnostics/audio/rom_source_wavehi_channelbc_replay_20261025/`.
4. **Source scheduling and CPU execution remain open.** Replace
   capture-framed cue placement with the decoded original scheduler and execute
   the original 6502 instruction/DMC-hook timing before considering a runtime
   WAV replacement. Do not call the current trace-driven diagnostic
   sample-exact or use its WAV as a Godot runtime asset.

## FCEUX APU bus alignment candidate (24 Oct 2026)

An isolated NSF trace was generated with `--cue-frame-offset 2` and compared
with a silent, same-input FCEUX APU bus capture. From the first `$58` cue
through the title stop sequence, all 45,450 writes to `$4000–$4013`, `$4015`,
and `$4017` match in address/value/order; this includes all 903 DMC register
writes. The first/last DMC writes and title-stop clear sequence use the same
alignment. The bus-trace run generated no PCM and used none as trace input; a
separate diagnostics-only libgme WAV was later rendered for the envelope
comparison below.

The trace timestamps need a clock mapping because the measured FCEUX replay
spans 139,730,109 CPU cycles over 4,692 elapsed frames while the NSF player
uses 29,780 CPU cycles per PLAY tick. Applying one rational scale
(`46,576,703 / 46,575,920`) and one median phase leaves residuals from about
−50 to +1,236 CPU cycles (RMS 307 cycles; maximum 0.691 ms at NTSC CPU rate).
This is strong register-sequence evidence, but it is not cycle-exact and does
not establish waveform equivalence. The production WAV and builder remain
unchanged pending an APU/DMC `WaveHi` renderer comparison through FCEUX's
stateful resampler/filter chain and a source explanation for the remaining
phase spread.

Report: `reference/diagnostics/audio/apu_write_timing_comparison_20261024.json`.
The isolated candidate trace is under
`reference/diagnostics/audio/rom_driver_apu_trace_cue_offset_plus2_20261024/`;
the FCEUX source trace is under
`reference/diagnostics/audio/fceux_apu_write_trace_20261024_184945_utc/`.

## Envelope comparison and current decision

Diagnostics-only WAVs were rendered from both the production NSF schedule and
the isolated +2-tick candidate through libgme, then compared with the existing
FCEUX PCM reference. Best full-file normalized correlation was 0.90907 for the
production schedule at −1 frame and 0.90901 for +2 at frame 0; the global
match is effectively unchanged. The first `$58` and loop `$58` windows improve
slightly under +2, while several later cue windows regress. Keep the production
WAV unchanged until an FCEUX-style source renderer is available.

The ROM's stop event clears APU channels on source frame 4662. FCEUX output
still contains stateful filter tail through frame 4679; the current production
WAV ends at frame 4661. The +2 libgme candidate is also not a valid tail fix:
its frame-4662 RMS is 1692.74 versus FCEUX 251.65 and it is silent by frame
4664, while FCEUX is at RMS 33.22 on frame 4670 and 1.48 on frame 4679. The
captured PCM is comparison-only and was not input to either render.

The source-backed implementation map is
`reference/rom_extract/audio/fceux_wavehi_implementation_map_20261024.md`.
An isolated tool now ports the pinned 1,024-tap `NeoFilterSound` resampler
(16.16 phase and 1,025-sample history) and persistent `SexyFilter` state:
`tools/audio/prototype_fceux_filter_pipeline.py` and
`tools/audio/fceux_filter_prototype/filter_pipeline.cpp`. It emits exactly
3,442,925 output samples over the measured frame-cycle blocks. Its input is a
sample-held, ROM-derived libgme signal, not FCEUX WaveHi; the output has overall
envelope correlation 0.90665 at frame offset 0 and stop-frame-4662 RMS 8,488
versus FCEUX 252. That discrepancy is expected from the surrogate input and
does not validate the complete audio output. The generated diagnostic WAV and
source metadata are in
`reference/diagnostics/audio/rom_driver_apu_trace_cue_offset_plus2_20261024/`.

The source-cycle APU→WaveHi diagnostic model now exists in
`tools/audio/fceux_apu_wavehi_prototype/apu_wavehi_renderer.cpp` and
`tools/audio/render_fceux_apu_wavehi_prototype.py`. It consumes the actual
cycle-stamped FCEUX APU write trace, models pulse, triangle, noise, and DMC
through the nonlinear mix and filter, and generates the expected 3,442,925
samples. DMC reads use the verified bank-`$1E` ROM windows. The full muted
FCEUX replay now supplies 104,106 fetches, 836,081 DMC bit-state snapshots,
832,848 `PCM_SYNC_IN` corrections, and 18,736 frame-sequencer timestamps. The
renderer pairs PCM-sync rows with their bit edges and schedules DAC changes at
`absolute_cycle - fudge` as `RDoPCM` reaches its corrected `SOUNDTS` boundary.
This is still a FCEUX-model trace for one input replay, not a physical NES or
arbitrary-input audio guarantee.

The ChannelBC-aware diagnostic has same-index correlations 0.99759 before
DMC, 0.99615 in the first DMC music window, 0.99696 in the later `$28`
sequence, 0.99604 in `$02`, 0.99565 in the late `$58` loop, 0.99663 in the
final `$68` cue, and 0.99426 in the stop/filter tail. This is a substantial

and corrected `PCM_SYNC_IN` boundary. Candidate RMS is still about 2–4% higher
and normalized RMSE is 7.3–11.5%; timing events remain captured FCEUX trace
inputs, so the renderer does not execute the original CPU/DMC hook. Full
metrics and hashes:
`reference/diagnostics/audio/rom_source_wavehi_channelbc_replay_20261025/validation_comparison.json`.
The diagnostic render is not a runtime asset; Godot's runtime WAV remains
unchanged.
